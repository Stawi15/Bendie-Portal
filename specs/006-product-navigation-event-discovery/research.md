# Phase 0 Research: Product-Level Navigation & Product-Aware Event Discovery

Each item follows Decision / Rationale / Alternatives considered. All findings are grounded in the actual current repository content read during planning (`OrganizationContext.tsx`, `EventContext.tsx`, `TopHeader.tsx`, `OrgSideNav.tsx`, `portal/layout.tsx`, `portal/page.tsx`, `portal/events/page.tsx`, `events/[eventId]/layout.tsx`, `useOrgEvents.ts`, `eventAuth.ts`, `portalAuth.ts`, `eventSectionMeta.ts`, `EventsOverviewPanel.tsx`, `CreateEventModal.tsx`, `eventColumns.ts`, `middleware.ts`, `src/types/database.ts`), not assumed from prior summaries.

## Q1 — Product-context derivation

**Decision**: A `ProductContext` React provider derives `product: 'bendie' | 'planner' | null` purely from `usePathname()` on every render (`/portal/bendie*` → `'bendie'`, `/portal/planner*` → `'planner'`, anything else → `null`). No internal state, no effect, no persistence — a pure computed value, mounted once in `portal/layout.tsx` alongside the existing `OrganizationProvider`/`EventProvider`.

**Rationale**: Spec FR-002 requires the URL to be the sole authority; a value computed fresh from `usePathname()` on every render cannot drift from the URL by construction — there is no separate state to go stale. This mirrors the read-only, derived nature already used for the product-navigation active-tab logic in `EventLayout.tsx` (`activeSectionKey` is derived from `pathname`, not stored).

**Alternatives considered**: A `useState` set by an effect watching `pathname` — rejected because it introduces a one-render lag and a redundant second source of truth for something a pure function already answers. `localStorage`/`profiles.current_product` — explicitly excluded by the spec (FR-002, Assumptions).

## Q2 — Product entitlement retrieval

**Decision**: A new function `getAvailableProducts(organizationId, client = supabase)` in `eventAuth.ts`, alongside the existing `isProductActiveForOrg`, doing one query: `organization_products.select('product_key, is_active').eq('organization_id', organizationId).eq('is_active', true)`, returning `{ bendie: boolean; planner: boolean }`.

**Rationale**: `CreateEventModal.tsx` already calls `isProductActiveForOrg` twice (once per product) — a single combined query is strictly better for the switcher and the new product-guard hook, which both need both flags at once. Placing it in `eventAuth.ts` keeps every product-truth read in one file, per Constitution II's "reuse existing helpers ... before writing new ones."

**Alternatives considered**: Extending `OrganizationContext` itself to carry `availableProducts` — rejected: `OrganizationContext` is organization identity/list only today, and not every organization consumer needs product data (adding it there would make every existing consumer of `useOrganization()` pay for a query it doesn't use). A new standalone `productAuth.ts` file — rejected as an unnecessary second file when `eventAuth.ts` already owns exactly this kind of read (`isProductActiveForOrg`, `isProductAvailableForEvent`).

## Q3 — Default-product resolver

**Decision**: One pure function, `resolveDefaultProduct(available: { bendie: boolean; planner: boolean }): 'bendie' | 'planner' | null` in a new `src/lib/productNavigation.ts`: bendie-only → `'bendie'`, planner-only → `'planner'`, both → `'bendie'`, neither → `null`. A second pure function, `resolveProductFallback(current, available)`, implements the org-switch preservation rule (FR-018/019): if `current` is still in `available`, return `current`; else return `resolveDefaultProduct(available)`.

**Rationale**: Spec explicitly requires "one canonical resolver," reused by the legacy `/portal`/`/portal/events` redirects, the per-product-page guard (organization switched away from an available product), and the event-workspace-to-org-switch landing (FR-054). A pure, dependency-free function is trivially reusable from both client components and (if ever needed) a server context, and is the only way to guarantee the three call sites can never silently diverge.

**Alternatives considered**: Duplicating the bendie/planner/both/none branching inline at each of the three call sites — rejected per spec's explicit "avoid reproducing this logic separately" instruction and Constitution I.

## Q4 — Product switcher architecture

**Decision**: Extend `TopHeader.tsx`'s existing organization-switcher dropdown pattern with a second, adjacent dropdown for product, visible only when `availableProducts` (from `getAvailableProducts(organizationId)`, loaded once per `organizationId`/`orgLoading` change, mirroring how `TopHeader` already loads `useOrgEvents`) yields at least one active product. Clicking an option calls a small resolver (`resolveProductSwitchDestination`, `productNavigation.ts`) that returns the destination path given: current pathname shape (`product-home` / `product-events` / `shared` / `event-workspace`), the target product, and — only for the event-workspace case — the current event's `event_products` membership (already available via `EventLayout`'s existing `productAvailability` state, threaded down or re-queried).

**Rationale**: The user's brief explicitly forbids a header redesign; the org switcher in `TopHeader.tsx` is a proven, already-responsive (mobile + desktop) dropdown pattern with identical requirements (list of choices, one active, click to switch). Reusing its markup/structure is the direct reading of Constitution V (reuse before inventing) and AGENTS.md's brownfield rules.

**Alternatives considered**: A new standalone product switcher component mounted separately in the page body — rejected as a second, competing navigation affordance the spec doesn't ask for and that risks visual inconsistency with the org switcher it sits beside.

## Q5 — Event-origin transport mechanism

**Decision**: A `?product=bendie|planner` query parameter, appended by every product-aware link into an event workspace (`EventsOverviewPanel`'s per-row link, and the product home's "next event" links). `EventLayout.tsx` reads it via `useSearchParams()`; any value other than the two valid keys is treated identically to "absent" (legacy behavior).

**Rationale**: Satisfies every constraint in the spec (FR-034): survives refresh (it's server-visible on load), works with back/forward (part of browser history natively), deep-linkable/shareable (a plain URL), requires no DB write, and — critically — old event URLs (with no query string at all) remain byte-for-byte valid, since an absent parameter is just the existing Feature 005 default path. It does not need to propagate to every subsequent in-event tab click: origin only needs to resolve the *entry* tab (dashboard vs. planner-overview) and the Both-event landing rule; every tab reached afterward is already gated purely by `EVENT_SECTIONS`' existing per-tab `product` classification and `productAvailability`, which do not depend on how the user arrived.

**Alternatives considered**: A route segment (`/portal/events/[eventId]/from/[product]/...`) — rejected: mass-migrates/duplicates the existing route shape the spec explicitly forbids touching (FR-003). Hidden React state passed via `router.push({ state })` — Next.js App Router has no such mechanism, and it would fail every "survives refresh"/"deep-linkable" requirement anyway.

## Q6 — Product-aware event retrieval

**Decision**: Extend `useOrgEvents(organizationId, orgLoading, product?)`. When `product` is supplied, the query becomes a single PostgREST inner-join embed filter: `.select(EVENTS_SELECT_COLUMNS_WITH_PRODUCT_FILTER).eq('organization_id', organizationId).eq('event_products.product_key', product)`, where `EVENTS_SELECT_COLUMNS_WITH_PRODUCT_FILTER` is a new template-literal `as const` export in `eventColumns.ts`: `` `${EVENTS_SELECT_COLUMNS}, event_products!inner(product_key)` as const ``. The embedded `event_products` array is stripped from each row before it enters component state, so `EventRow`'s shape stays identical for both the filtered and unfiltered call sites.

**Rationale**: `event_products!inner(...)` is PostgREST's standard inner-join-embed syntax; because `event_products.event_id` already has a foreign key to `events.id` (Feature 002), PostgREST recognizes the relationship automatically — no new grant, no new view, no migration. This filters at the query layer (never "fetch all, hide client-side" — the exact anti-pattern the spec calls out), in a single round trip, and is a small, additive change to the one existing hook every event-list surface already shares (`portal/page.tsx`, `portal/events/page.tsx`, `TopHeader`'s search) — not a second, parallel fetch implementation.

**Alternatives considered**: Two-step query (fetch matching `event_id`s from `event_products`, then `.in('id', ids)` on `events`) — functionally equivalent and still query-layer filtering, but costs an extra round trip for no benefit once the single-query embed filter was confirmed to work against the existing schema; kept as the documented fallback if the embed filter is found to behave unexpectedly during implementation. A brand-new `useProductEvents` hook duplicating `useOrgEvents` — rejected: exactly the "duplicate event-fetch paths" the spec explicitly warns against.

## Q7 — Product home / product events page implementation

**Decision**: Extract `portal/page.tsx`'s existing JSX/logic into a shared component, `OrganizationHome` (co-located under `src/app/portal/bendie/page.tsx`/`src/app/portal/planner/page.tsx` via a small shared internal component, not a new `components/portal/` export unless reuse across a third call site emerges), parameterized by `product: ProductKey`, feeding `product` into `useOrgEvents(organizationId, orgLoading, product)`. Every event-derived figure (active count, upcoming count, next event, "Needs Attention," recent activity, shared-speakers) is computed from that product-filtered `events` array, unchanged in logic otherwise. Similarly, `portal/events/page.tsx`'s logic becomes a shared `product`-parameterized component reused by `bendie/events/page.tsx` and `planner/events/page.tsx`.

**Rationale**: "Reuse existing components where semantically valid, but make their event data product-aware," and "do not create large new Planner dashboards" (spec). Since `facilitators`/`agenda_sessions`/`emergency_contacts` queries in the Overview page are already keyed off the (now product-filtered) `events` array, they naturally become product-correct with zero additional special-casing — a Planner-only event simply won't contribute rows to those Bendie-shaped panels, which is the correct behavior, not a gap requiring a redesign.

**Alternatives considered**: Two independently written page implementations for Bendie vs. Planner homes — rejected: guaranteed drift over time and directly contradicts "avoid reproducing logic separately." A single page component keyed by a route param instead of two literal route folders — rejected: the spec's settled architecture names four literal routes; a catch-all would also complicate the simple `usePathname()`-based `ProductContext` derivation from Q1.

## Q8 — Organization-switching interaction

**Decision**: Each of the four product pages (and the two legacy redirects) runs a small `useProductGuard(desiredProduct)` hook: on `organizationId`/`orgLoading` change, call `getAvailableProducts(organizationId)`; if `desiredProduct` is in the result, render normally; otherwise `router.replace()` to `resolveProductFallback(desiredProduct, available)`'s result (same path-shape — home stays home, events stays events) or to `/portal/no-product` if the fallback is `null`. A generation ref (matching `EventContext`'s established pattern) guards against a rapid double-switch resolving out of order.

**Rationale**: Directly implements FR-017–FR-020 using the Q3 resolver, and reuses the exact stale-response protection pattern already proven in this codebase (`EventContext.tsx`'s `eventGenerationRef`/`workspaceGenerationRef`) rather than inventing a new one.

**Alternatives considered**: Centralizing this check once in `portal/layout.tsx` for every route — rejected: the layout does not know which product a given child route "wants" without inspecting the pathname a second time, and the four page-level call sites already need the resolved availability for their own rendering (switcher, empty states) regardless.

## Q9 — Event-workspace switching (deliberate) and mismatched-origin redirect

**Correction (2026-09-17, post-`/speckit.analyze` finding H1)**: the decision below originally directed the product switcher (owned by `TopHeader.tsx`) to source the current event's product membership from `EventLayout`'s local `productAvailability` state "via `useEvent()`." That data path does not exist: `productAvailability` is `useState` private to `EventLayout.tsx` and was never added to `EventContextType` (`src/contexts/EventContext.tsx`), and `TopHeader` is a **sibling** of the event-route subtree under `portal/layout.tsx`, not a descendant of `EventLayout` — there is no parent/child relationship for `useEvent()` (or any other existing hook) to expose that state through. The corrected decision below replaces that sourcing mechanism; it does not change any observable product behavior, routing outcome, or the mismatched-origin mechanism (point 2), which was already correct as written (it runs *inside* `EventLayout`, reading its own local state, which is legitimate).

**Decision**: Two distinct mechanisms, matching the clarification's explicit distinction:
1. **Deliberate switch** (FR-052/053): `TopHeader`'s product switcher, when clicked while `location === 'event-workspace'`, does **not** read any precomputed membership map. Instead, at click-time, it calls the already-existing `isProductAvailableForEvent(currentEventId, organizationId, targetProduct)` (`src/lib/eventAuth.ts`) directly — `currentEventId` comes from `useEvent()` (already exposed today) and `organizationId` from `useOrganization()` (already exposed today), both legitimately available to `TopHeader` as it already consumes both hooks. The resulting boolean is passed as `resolveProductSwitchDestination`'s `eventProductMembership[targetProduct]` input (contract 4 is unchanged — it was always agnostic about how the caller obtains that boolean). If `true`, `router.push` directly to that event's corresponding entry tab (`dashboard` or `planner-overview`) with `?product=<target>`; otherwise `router.push` to the target product's `/events` list. This introduces no new query, no new API, and no `EventContext` expansion — it is a single additional call to a function `EventLayout` itself already calls per-product in its own effect, from a different component, at a different moment (click-time rather than mount-time).
2. **Mismatched-origin/direct-URL safety net** (FR-038/039): `EventLayout.tsx`'s existing Planner-only redirect effect (today: `dashboard` + `!bendie` + `planner available` → `planner-overview`) is generalized to a bidirectional rule: whenever `activeSection.product` is `'bendie'` or `'planner'`, is unavailable for this event, and the OTHER product IS available, redirect to that other product's entry tab. This subsumes today's one-directional case as a special instance and remains loop-safe by the same reasoning already documented in the existing code comment (the destination tab is, by construction, available, so the condition cannot re-fire). This mechanism is unaffected by the H1 correction — it already read only `EventLayout`'s own local state, which is legitimate since the redirect effect lives inside `EventLayout` itself.

**Rationale**: The clarification session explicitly separated "deliberately switching products while inside an event" from "opening an event carrying a mismatched origin signal" as potentially different behaviors, and the spec (FR-052/053 vs. FR-038/039) keeps them distinct. The corrected deliberate-switch mechanism reuses the exact same existing, narrow helper `EventLayout` already relies on (`isProductAvailableForEvent`) rather than inventing a second product-membership data source, so "avoid duplicate entitlement/membership resolvers" is still satisfied — it is a second *call site* of the same function, not a second *implementation*.

**Alternatives considered**: A single unified redirect effect handling both deliberate switches and mismatched direct URLs — rejected: a deliberate switch has a specific, current-user-chosen target product and knows immediately whether to land in-event or in the target product's list (no need to wait for a redirect effect to react to a URL that hasn't changed yet), while the safety net must be resilient to a URL arriving from anywhere (bookmark, share, stale tab). Conflating them would make the resulting effect harder to reason about, not simpler. *(H1 remediation alternatives)*: lifting `productAvailability` into `EventContext` — rejected: would expand a shared context's type merely to satisfy one click-time check `TopHeader` can already answer itself with an existing function call, and would leave the same data computed twice (once in `EventContext`, once in `EventLayout`'s own effect) unless `EventLayout` were also refactored to consume it from context, which is a materially larger, unjustified change for this fix. Prop-drilling or a new dedicated context solely for this value — rejected as a second, competing product-membership data source for no benefit over calling the existing helper directly.

**Organization switch while inside an event workspace (FR-054)**: a third, separate effect in `EventLayout.tsx` tracks `organizationId` via a `prevOrgIdRef`. When `organizationId` changes to a new non-null value while the layout is mounted (a real organization switch, not the initial mount), the effect immediately computes `getAvailableProducts(newOrgId)` → `resolveDefaultProduct(...)` and `router.replace()`s to that product's home — pre-empting the (still-correct, but slower and less friendly) fallback of merely letting `checkWorkspaceAccess` re-deny the old event against the new organization. Guarded by its own generation ref (Q12) so a rapid double organization-switch cannot resolve out of order. This is additive to, not a replacement for, the existing workspace-access re-check — that re-check still independently denies the old event if this redirect were ever somehow bypassed, matching Constitution IV's "every privileged action re-verifies independently."

**Correction (2026-09-17, post-`/speckit.analyze` finding L1)**: because both the new redirect effect and the existing `checkWorkspaceAccess` re-check react to the same `organizationId` change, and `router.replace()` is asynchronous, the existing `workspaceAuthDenied` render ("You don't have access to this event") could otherwise paint for one frame before the redirect completes — telling the user they lack access to an event they simply switched away from, which is misleading even though no data is exposed. The effect must therefore set a local `orgSwitchRedirecting` flag (`useState`, scoped to `EventLayout`) synchronously in the same tick it detects the organization change and *before* calling `router.replace()`; while that flag is `true`, `EventLayout` renders its **existing** `workspaceAuthPending` loading-skeleton branch (the same skeleton already used for the pre-authorization loading state — no new loading UI is designed) instead of evaluating `workspaceAuthDenied`. This guarantees the old event's content and the misleading "no access" message are both replaced by a neutral, already-established loading treatment for the single frame(s) until navigation completes, and never displays old-event data as current during that window.

## Q10 — Legacy `/portal` and `/portal/events` redirect implementation

**Decision**: Both routes become minimal client components: resolve `availableProducts` for the current `organizationId` via `getAvailableProducts`, compute `resolveDefaultProduct(available)`, and `router.replace()` to `/portal/${resolvedProduct}` (for `/portal`) or `/portal/${resolvedProduct}/events` (for `/portal/events`) — or `/portal/no-product` if `resolvedProduct` is `null`. While `organizationId`/`availableProducts` are resolving, render the same loading skeleton pattern already used elsewhere in the portal shell (e.g., `portal/loading.tsx`'s existing skeleton shape).

**Rationale**: Directly implements FR-055/FR-056 using the Q3 canonical resolver, keeping the "avoid reproducing this logic separately" guarantee — these two routes are simply two more callers of the same resolver used by Q8's guard.

**Alternatives considered**: A `middleware.ts` redirect — rejected: `middleware.ts` runs before Supabase RLS-governed data is convenient to fetch (it already does two extra round-trips for role/membership caching per the existing code, and product-entitlement resolution needs the *selected* organization, which is client-side profile/context state today, not something middleware currently resolves); doing this client-side keeps it consistent with how `OrganizationContext` itself resolves organization selection (client-side, not middleware).

## Q11 — No-product state

**Decision**: A new route `src/app/portal/no-product/page.tsx`, structurally parallel to the existing `src/app/portal/no-access/page.tsx` (read during planning to confirm the established pattern for this class of state) — a centered, friendly message explaining the organization currently has no active Bendie or Bendie Planner entitlement, with no product switcher rendered (since there is nothing to switch to) and no event-discovery content. `OrgSideNav`'s shared-page links remain visible and functional (FR-048) since `OrgSideNav` itself is not product-gated.

**Rationale**: Matches the codebase's own established precedent for a "safe state, not an error" page (`/portal/no-access`, already reachable outside the membership gate in `middleware.ts`) rather than inventing a new visual pattern.

**Alternatives considered**: Reusing `/portal/no-access` itself for this case — rejected: that page's copy/meaning is specifically "you have no organization membership," a materially different condition from "your organization has no product entitlement," and conflating them would be misleading to the user.

## Q12 — Stale-response / race protection

**Decision**: Add a generation-ref guard directly inside `useOrgEvents.ts`'s `refetch` (currently unguarded — confirmed by reading the file), following the exact pattern already proven in `EventContext.tsx`. `useProductGuard` (Q8) gets its own independent generation ref for the same reason `EventContext` uses two independent counters rather than one shared counter (each guards state only its own effect writes).

**Rationale**: `useOrgEvents` is now called with a `product` argument that can change on every product/organization switch — a scenario that did not exist before this feature and makes the previously-latent lack of staleness protection in this specific hook newly load-bearing (FR-049/050). This is a narrowly-scoped, bug-fix-shaped addition to an existing shared hook, not a new abstraction, and reuses rather than reinvents the established pattern.

**Alternatives considered**: Leaving `useOrgEvents` unguarded and relying on React's unmount/cleanup alone — insufficient, since the hook is called from the same mounted component across a product/org switch (the component doesn't unmount, only its arguments change), which is exactly the scenario `EventContext`'s own code comments document as the specific gap a simple "is this still mounted" check cannot close.

## Q13 — Server/client authorization boundary

**Decision**: No new authorization boundary is introduced. Every product-truth read (`getAvailableProducts`, `isProductActiveForOrg`, `isProductAvailableForEvent`) continues to run through the existing RLS-governed browser client, exactly as `CreateEventModal.tsx` and `EventLayout.tsx` already do today — Feature 006 adds no service-role client and no new `app/api/**` route. Event-workspace authorization (`requireEventWorkspaceAccess`) and its precedence ahead of any product-based routing decision (FR-058) is preserved exactly as implemented today in `EventLayout.tsx` (the `workspaceAuthPending`/`workspaceAuthDenied` early-return gates run and are resolved before the product-availability/redirect logic is ever evaluated) — the new mismatched-product redirect logic (Q9) is added strictly after that existing gate, never before it.

**Rationale**: Constitution IV (least privilege) and FR-004/FR-058 both require product navigation to never become, or precede, an authorization decision. The existing `EventLayout.tsx` code structure already enforces the correct order; the plan's only obligation is to preserve it, which is called out explicitly here so implementation does not accidentally hoist the new redirect logic above the existing auth gates.

**Alternatives considered**: None — this is a preservation requirement, not a design choice with genuine alternatives.
