# Feature Specification: Bendie Planner Tasks Management

**Feature Branch**: `007-bendie-planner-tasks-management`

**Created**: 2026-09-17

**Status**: Draft

**Input**: User description: "Introduce the first real writable Bendie Planner management module inside Bendie Portal: Tasks Management, operating against the existing live Planner `operational_tasks` table, for Planner-only and Both events."

## Context

Features 001–006 are converged. Feature 005 introduced a read-only Planner Overview; Feature 006 established product-level navigation, product-aware event discovery, and the URL-authoritative `?product=` origin model. The Feature 007 architecture/discovery pass inspected the live Planner Supabase project (`zghoaawgrmvqdlksuiam`) directly and found `operational_tasks` to be a mature, actively-used (500+ live rows), cleanly-modeled domain with no Bendie equivalent — making it the first coherent Planner management slice with zero cross-product synchronization conflict.

That discovery pass also surfaced concrete, evidence-based facts this specification treats as authoritative:

- `operational_tasks` has a live native RLS policy (`operational_tasks_write_self_or_manager_or_admin`) expressing exactly which Planner-authenticated caller may write a row: a Planner platform admin, the task's own assignee, or a caller with an active `event_user_assignments` row for that event with `can_manage_tasks = true`.
- `status` is constrained (CHECK) to exactly `pending` / `in progress` / `completed`; `priority` to exactly `low` / `medium` / `high` (case-insensitive, canonicalized to Title Case by an existing trigger).
- `task_code` is generated by an existing, race-safe Planner function, `next_event_task_code(event_id)`, which atomically increments `event_task_counters` and formats `{event_code}-{0000}`.
- `assigned_profile_id` references the modern Planner `profiles.id` (bridged from Portal via `profiles.planner_profile_id`, established in Feature 001) — never the legacy `users` table.
- An existing Planner mobile-app RPC (`update_my_task`) already lets a self-assignee edit more than status/remarks, and in one variant even reassign — evidence this specification deliberately does **not** carry into the Portal surface (see Clarifications and FR-024).
- An existing helper (`get_task_assignable_profiles`) returns every named Planner profile organization-wide, not scoped to the event's own staff assignments — this specification deliberately does not reuse it (see FR-029).
- A separate helper (`resolve_profile_for_task`) performs fuzzy name matching with a **random-profile fallback** when no match is found — built for legacy bulk-import convenience; this specification explicitly forbids its use for any interactive assignment (see FR-030).
- The existing task-writing RPCs (`create_operational_task`, `update_my_task`, `update_operational_task_status`) all gate on Planner's own `auth.uid()`, which the Portal server's service-role connection does not have — so Feature 007 cannot call them directly and must instead perform direct table operations via the service-role client, independently re-implementing the equivalent permission check server-side (mirroring, not weakening, the native RLS intent).

## Clarifications

### Session 2026-09-17 (resolved during architecture discovery and specification, no product-owner input required)

- Q: Does creating a task require management permission, or does the native RLS's self-assignee branch also apply to creation? → A: Creation is a management operation and requires `can_manage_tasks` (or Planner platform-admin) in the Portal surface, even though the live RLS technically also permits self-assigned creation by any caller — deliberately narrower for safety (FR-019).
- Q: How far can a self-assignee (without `can_manage_tasks`) edit their own task? → A: Status and remarks only. Reassignment, title, category, due date, and priority remain manager-only, even though the existing Planner mobile app's own self-service RPC currently permits more (FR-022–FR-024).
- Q: Where does the assignable-staff list for a task come from? → A: The event's own active `event_user_assignments` rows joined to `profiles`, never the existing organization-wide `get_task_assignable_profiles` helper (FR-029).
- Q: Does Feature 007 need a new archive/soft-delete concept? → A: No — the schema has no such column; deletion, where permitted, is a hard delete restricted to managers/platform-admin (FR-026).
- Q: Does Feature 007 need an optimistic-locking mechanism? → A: No — mutations are server-authoritative with post-mutation refetch; simultaneous-edit overwrite is an accepted, documented limitation (FR-043/FR-044).

### Session 2026-09-18 (post-implementation `/code-review` correction, no product-owner input required)

- Q: Does resubmitting a task's own unchanged `assigned_profile_id` in a manager PATCH count as a reassignment requiring active-assignment validation? → A: No. This was found, during post-implementation review, to be underspecified in the original FR-053 wording in a way that — read literally — would block a manager from editing any unrelated field (priority, due date, title, ...) on a task whose historical assignee had since become inactive, contradicting FR-032's own intent that historical assignment be preserved rather than become an edit-blocker. FR-053 corrected to make the distinction explicit: validation applies only to a genuine reassignment (a submitted `assigned_profile_id` that is non-null and differs from the currently persisted value); resubmitting the exact persisted value is always allowed regardless of that assignee's current active status; omission leaves assignment untouched; explicit `null` is always allowed as deliberate unassignment. No change to FR-029/FR-030/FR-034's substance — a genuine reassignment still requires validation against the current active, event-scoped assignable staff list exactly as before.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A Planner manager creates and manages event tasks (Priority: P1)

An organization member with Planner task-management permission for an event can create tasks, edit their details, reassign them, change their status, and delete them, all without leaving the Portal event workspace.

**Why this priority**: This is the entire value proposition of Feature 007 — without real create/edit capability, there is no writable Planner management module at all.

**Independent Test**: As a Portal user whose synced Planner profile has an active `event_user_assignments` row with `can_manage_tasks = true` for a Planner-only or Both event, open the Tasks module, create a task, edit it, reassign it, change its status, and delete it — each operation succeeds and the list reflects the change after refetch.

**Acceptance Scenarios**:

1. **Given** a manager-permission user on a Planner-only event, **When** they create a task with a title, category, priority, due date, and assignee, **Then** the task is created with status "Pending" and a system-generated `task_code`.
2. **Given** an existing task, **When** the manager edits its title, category, due date, or priority, **Then** the change is saved and reflected after the list refetches.
3. **Given** an existing task, **When** the manager reassigns it to a different staff member who has an active assignment for this event, **Then** the reassignment succeeds.
4. **Given** an existing task, **When** the manager changes its status among Pending/In Progress/Completed, **Then** the change is saved.
5. **Given** an existing task, **When** the manager deletes it, **Then** it is permanently removed and no longer appears in the list.
6. **Given** a manager attempts to reassign a task to a profile with no active assignment for this event, **When** they submit the change, **Then** the server rejects it.

---

### User Story 2 - A Planner staff member updates their own assigned tasks (Priority: P1)

A staff member assigned to a task, who does not hold management permission, can see their tasks and update the status and remarks of tasks assigned to them, without being able to alter the task's structural details or reassign it.

**Why this priority**: This is the day-to-day, highest-frequency interaction the Tasks module exists to support — an ordinary staff member marking their own work as in-progress or done.

**Independent Test**: As a Portal user whose synced Planner profile is the assignee of a task but whose `event_user_assignments` row has `can_manage_tasks = false`, open the Tasks module, change the status and remarks of a task assigned to them, and confirm an attempt to change its title, category, due date, priority, or assignee is rejected.

**Acceptance Scenarios**:

1. **Given** a task assigned to the caller, **When** they change its status, **Then** the change succeeds.
2. **Given** a task assigned to the caller, **When** they edit its remarks, **Then** the change succeeds.
3. **Given** a task assigned to the caller, **When** they attempt to change its title, category, due date, priority, or assignee, **Then** the server rejects the attempt.
4. **Given** a task assigned to a *different* user, **When** the caller attempts any change to it, **Then** the server rejects the attempt (no management permission and not the assignee).

---

### User Story 3 - A view-only Planner staff member sees the task list without edit controls (Priority: P2)

A staff member with view-only Planner access to an event can open the Tasks module and see the full task list and detail, but every mutation control is unavailable to them.

**Why this priority**: Establishes the read/write distinction the native Planner permission model already expresses; necessary for a coherent module but secondary to actually being able to write.

**Independent Test**: As a Portal user whose synced Planner profile has an active `event_user_assignments` row with `can_view_tasks = true` and `can_manage_tasks = false`, and who is not the assignee of any task shown, open the Tasks module and confirm the list renders with no create/edit/delete/reassign affordance available.

**Acceptance Scenarios**:

1. **Given** a view-only user, **When** they open the Tasks module, **Then** they see the full task list (title, code, status, priority, category, due date, assignee) for the event.
2. **Given** a view-only user, **When** they look for a create-task action, **Then** none is available to them.
3. **Given** a view-only user, **When** they open a task they do not own, **Then** no edit/reassign/delete control is available.

---

### User Story 4 - Tasks is unavailable where it should be (Priority: P1)

A user without any qualifying Planner presence for an event, or viewing a Bendie-only event, never sees the Tasks module and cannot reach it via a direct URL either.

**Why this priority**: Security/boundary-correctness is not optional for a first writable module — this must be right from the start.

**Independent Test**: As (a) an ordinary Portal event member with no synced Planner profile, and separately (b) any authorized user viewing a Bendie-only event, confirm the Tasks tab does not appear in navigation and a direct visit to its route is denied.

**Acceptance Scenarios**:

1. **Given** a Bendie-only event, **When** any user views the event workspace, **Then** no Planner Tasks tab appears, and a direct route visit is denied.
2. **Given** a Planner-only or Both event, **When** a Portal event member with no synced Planner profile views the workspace, **Then** no Planner Tasks tab appears, and a direct route visit is denied — never a "Planner staff setup required" management-style state.
3. **Given** a Portal user who lacks even Feature 003 event-workspace access, **When** they attempt the Tasks route directly, **Then** they are denied exactly as any other event-workspace route denies them, before any Planner-specific check occurs.
4. **Given** a request carrying an arbitrary or mismatched `?product=` value, **When** it reaches the Tasks route, **Then** authorization outcome is unaffected by that parameter.

---

### User Story 5 - Reassignment only offers valid staff (Priority: P2)

When a manager reassigns a task, only staff genuinely assigned to that specific event are offered, and the system behaves safely when a previously-assigned staff member is no longer active or resolvable.

**Why this priority**: Prevents a subtle but real data-integrity/privacy issue (exposing organization-wide Planner identities) and a broken-reference failure mode.

**Independent Test**: As a manager-permission user, open the reassignment control and confirm only staff with an active assignment for this specific event appear; separately, view a task whose previously-assigned staff member has since become inactive or unresolvable and confirm it renders safely.

**Acceptance Scenarios**:

1. **Given** an event with several staff assignments, **When** a manager opens the assignee picker for a task, **Then** only profiles with an active `event_user_assignments` row for *this* event are offered.
2. **Given** a task assigned to a staff member whose assignment has since become inactive, **When** the task is viewed, **Then** the task still displays its historical assignee with an indication they are no longer active, rather than the assignment being silently cleared or rewritten.
3. **Given** a task whose assigned profile can no longer be resolved at all, **When** the task is viewed, **Then** a safe fallback label is shown rather than a rendering failure.

---

### Edge Cases

- A task is created with `status` defaulted to "Pending" regardless of any client-supplied value — status is not a create-time field.
- A due date value that is not a valid date is rejected rather than silently stored.
- A missing task title is rejected on create and on edit.
- An invalid `status` or `priority` value (outside the exact enumerated set) is rejected, never coerced to a guess.
- A `taskId` that does not belong to the resolved event is rejected as not found, never silently reinterpreted against a different event.
- A canonical Planner link that is missing or inactive for an otherwise Planner-eligible event renders a distinct "not yet configured" state, never an empty task list.
- A genuine Planner read or write failure renders a distinct error state, never an empty task list and never raw diagnostic detail.
- Two users editing the same task at nearly the same time: the later successful write wins; no corruption, no merge — an accepted limitation.
- A manager deletes a task while another user is viewing it: the viewer's next refetch reflects its absence; no crash on stale local state.
- Filtering the task list by status, priority, or assignee narrows the same underlying result set consistently with the unfiltered counts.
- A Both event's Tasks module contains only Planner-native tasks; it never displays or is confused with Bendie's own event content.
- Rapid navigation away from the Tasks module while a mutation is in flight does not apply a stale result to a since-navigated-away view.

## Requirements *(mandatory)*

### Functional Requirements

**Product boundary and availability**

- **FR-001**: The Tasks module MUST be available only for an event whose Planner product is active (Planner-only or Both) and whose canonical Planner counterpart exists; it MUST NOT be available for a Bendie-only event.
- **FR-002**: The Tasks module MUST resolve the Planner counterpart exclusively via the existing canonical `event_planner_links` mapping; no second mapping mechanism may be introduced.
- **FR-003**: The Tasks module introduces no synchronization with Bendie data in either direction; tasks remain exclusively Planner-owned data for both Planner-only and Both events.
- **FR-004**: The Tasks navigation tab MUST NOT appear for a Bendie-only event.
- **FR-005**: Direct route or API access to Tasks for a Bendie-only event MUST be denied independently of tab visibility.
- **FR-006**: Accessing the Tasks module MUST NOT trigger Planner provisioning for an event that lacks it.

**Portal authorization precedence**

- **FR-007**: Feature 003 event-workspace access MUST be established before any Planner-specific Tasks check is evaluated.
- **FR-008**: Organization membership alone MUST NOT be sufficient for Tasks access.
- **FR-009**: A `?product=` query parameter MUST NOT influence any authorization or permission outcome for Tasks.
- **FR-010**: Every mutation MUST independently re-verify server-side permission immediately before acting, regardless of any earlier page-level check.

**Identity resolution**

- **FR-011**: The acting user's Planner identity MUST be resolved solely via the existing Portal↔Planner bridge (`profiles.planner_profile_id`, Feature 001); no new identity-mapping mechanism may be introduced.
- **FR-012**: Tasks MUST NOT be mapped to Planner `passengers`, and assignment MUST NOT use the legacy Planner `users` table.
- **FR-013**: A Portal user with no synced Planner profile MUST NOT be able to access the Tasks module (module hidden from navigation; direct access denied) — never shown a degraded "Planner staff setup required" management state.
- **FR-014**: A Portal user whose synced Planner profile has no active `event_user_assignments` row for this event (or one with neither `can_view_tasks` nor `can_manage_tasks` set) MUST NOT be able to access the Tasks module, per the same rule as FR-013.

**Read permission**

- **FR-015**: A user whose active `event_user_assignments` row for this event has `can_view_tasks = true` or `can_manage_tasks = true` MUST be able to view the task list and task detail.
- **FR-016**: The task list and every task detail MUST be scoped strictly to the resolved canonical Planner event; cross-event task data MUST NOT be retrievable through this module.
- **FR-017**: An event with zero tasks and an active, correctly-configured Tasks module MUST render as a normal, successful empty state.
- **FR-018**: A user who does not satisfy FR-015 MUST NOT receive a degraded or partial Tasks view; they receive the same denial as FR-013/FR-014.

**Write permission — per operation**

- **FR-019**: Creating a task MUST require `can_manage_tasks = true` (or Planner platform-admin); self-assignment alone MUST NOT authorize creation in the Portal surface (a deliberate narrowing versus the live Planner RLS, which technically also permits self-assigned creation — see Clarifications).
- **FR-020**: A newly created task MUST always be created with status "Pending"; status MUST NOT be a client-selectable field at creation time.
- **FR-021**: Editing a task's title, category, due date, or priority MUST require `can_manage_tasks = true` (or Planner platform-admin).
- **FR-022**: Changing a task's status MUST be permitted for `can_manage_tasks = true` (or platform-admin) AND additionally for the task's current assignee acting on their own assigned task.
- **FR-023**: Editing a task's remarks MUST be permitted under the same rule as FR-022.
- **FR-024**: A caller who qualifies only as the task's assignee (without `can_manage_tasks`) MUST NOT be able to change the task's title, category, due date, priority, or assignee, and MUST NOT be able to modify `event_id`, `task_id`, `task_code`, or `created_by_profile_id` under any circumstance — a deliberate narrowing versus the existing Planner mobile app's own self-service update capability, which currently permits more (see Clarifications).
- **FR-025**: Reassigning a task (changing `assigned_profile_id`) MUST require `can_manage_tasks = true` (or Planner platform-admin).
- **FR-026**: Deleting a task MUST require `can_manage_tasks = true` (or Planner platform-admin); deletion is a hard delete, since the schema has no archive/soft-delete field; a task's assignee alone MUST NOT be able to delete it.
- **FR-027**: No Feature 007 operation may change a task's `event_id`.
- **FR-028**: Every write MUST independently re-validate, server-side, that the targeted `taskId` belongs to the resolved event before proceeding; a mismatch MUST be treated as not-found, not silently redirected to another event's task.

**Assignment model**

- **FR-029**: The list of assignable staff for a task MUST be derived from that event's own active `event_user_assignments` rows joined to `profiles`; the existing organization-wide, event-agnostic helper MUST NOT be used for this purpose.
- **FR-030**: Assignment MUST be by explicit, validated profile selection only; fuzzy name-matching or any random-fallback resolution MUST NOT be used.
- **FR-031**: A task MAY be unassigned (no current assignee).
- **FR-032**: If an assigned staff member's event assignment later becomes inactive, the task's historical assignment record MUST be preserved (not cleared or rewritten); the assignee MUST be shown with an indication that they are no longer an active event staff member.
- **FR-033**: If an assigned profile can no longer be resolved at all, the UI MUST show a safe fallback label rather than failing to render.
- **FR-034**: Reassigning a task to a given profile MUST first validate that the profile currently has an active `event_user_assignments` row for this event; otherwise the reassignment MUST be rejected.

**Task list**

- **FR-035**: The task list MUST show, at minimum, for each task: title, task code, status, priority, category, due date, and assignee.
- **FR-036**: The task list MUST support filtering by status, by priority, and by assignee.
- **FR-037**: The task list MUST be scoped to a single event; no aggregated multi-event view is in scope.
- **FR-038**: The task list's default ordering MUST be by due date ascending (nulls last), consistent with existing Planner precedent.

**Task code**

- **FR-039**: A task's `task_code` MUST be generated exclusively via the existing Planner `next_event_task_code` mechanism; no second code-generation scheme may be introduced, and the client MUST NOT generate or submit a task code.
- **FR-040**: `task_code` MUST be displayed but MUST NOT be editable by any caller.

**Status / priority vocabulary**

- **FR-041**: `status` MUST be restricted to exactly Pending / In Progress / Completed; any other submitted value MUST be rejected.
- **FR-042**: `priority` MUST be restricted to exactly Low / Medium / High; any other submitted value MUST be rejected.

**Concurrency**

- **FR-043**: Every mutation MUST be server-authoritative; after a successful mutation, the client MUST reconcile against the server's authoritative response (or a fresh refetch) rather than trusting only optimistic local state.
- **FR-044**: Simultaneous edits to the same task by two different callers MAY result in a last-write-wins outcome; this is an accepted limitation for Feature 007, and no version/optimistic-locking column may be introduced to prevent it.

**Error and state semantics**

- **FR-045**: A genuine Planner read or write failure MUST render a distinct error state and MUST NOT be presented as "zero tasks."
- **FR-046**: A genuinely empty task list (per FR-017) MUST be visually and semantically distinct from an error state.
- **FR-047**: The no-synced-Planner-identity state (FR-013) MUST be realized as the module's absence from navigation plus a direct-access denial, not a distinct visible "set up Planner access" screen.
- **FR-048**: A missing or inactive canonical Planner link for an otherwise Planner-eligible event MUST render as a distinct event-configuration state, never as an empty task list or a generic error.
- **FR-049**: A loading/pending resolution state MUST be shown while authorization or data is still resolving; no wrong-permission or wrong-data content may render during that window.
- **FR-050**: A write failure MUST present a distinct, safe error message and MUST NOT expose raw Planner error text, stack traces, or diagnostic detail.

**Security**

- **FR-051**: Planner service-role credentials MUST never be reachable from the browser.
- **FR-052**: The client MUST NOT supply or select the Planner event ID directly; it MUST always be resolved server-side from the Portal event ID via `event_planner_links`.
- **FR-053**: A client-submitted `assigned_profile_id` that constitutes a genuine reassignment — present in the request AND non-null AND different from the task's currently persisted `assigned_profile_id` — MUST be validated server-side against the event's current active assignment list (FR-034) before being trusted for any write. Resubmitting the exact currently persisted `assigned_profile_id` unchanged is NOT a reassignment and MUST be allowed even when that assignee's `event_user_assignments` row is now inactive or otherwise unresolvable (FR-032) — the exemption applies only to that exact trusted, server-read persisted value, never to any other inactive, historical, cross-event, or arbitrary profile. Omitting `assigned_profile_id` from the request MUST leave the existing assignment untouched with no validation performed. Explicitly submitting `null` MUST be treated as a deliberate unassignment and MUST always be allowed without validation. *(Corrected `/code-review` M1/D1 — the original wording read as an unconditional validate-on-every-write rule that, taken literally, would re-permit the M1 defect: blocking an unrelated edit merely because the task's unchanged historical assignee is no longer active.)*
- **FR-054**: No cross-event task access is permitted: a task ID MUST be verified to belong to the resolved event before any read or write proceeds (restates FR-028 as a security requirement).
- **FR-055**: No cross-organization access is permitted: the resolved canonical event mapping MUST belong to the organization the caller's Portal session is scoped to, per existing Feature 003 scoping.
- **FR-056**: A `?product=` query parameter MUST NOT be consulted by any authorization or permission check (restates FR-009 as a security requirement).
- **FR-057**: Every mutation MUST independently re-verify server-side permission immediately before acting (restates FR-010 as a security requirement).
- **FR-058**: API responses MUST NOT include raw Planner rows/columns beyond an explicit, safe, documented allowlist, and MUST NOT include raw Planner error objects.

**Navigation**

- **FR-059**: A new `EVENT_SECTIONS` entry for Tasks MUST be classified `product: 'planner'` for access-gating purposes only, consistent with the Feature 006 distinction between access-gating classification and current-product identity.
- **FR-060**: The Tasks tab MUST NOT be treated as a self-determining product-entry section; it MUST inherit/preserve the existing `?product=` origin signal exactly as every other non-entry event tab does, per Feature 006's settled `resolveEventTabProduct` rule.

### Key Entities

- **Planner Task** (`operational_tasks`, existing, read/write from this feature): a single task scoped to one Planner event, with title, category, status, priority, due date, remarks, assignee, task code, and audit fields (creator, timestamps). Never mapped to Bendie data.
- **Planner Event Assignment** (`event_user_assignments`, existing, read-only from this feature): the native Planner per-event, per-profile permission record (`can_view_tasks`, `can_manage_tasks`, `is_active`, among others) this feature's authorization model mirrors server-side; never written by this feature.
- **Planner Profile** (`profiles`, existing, read-only from this feature): the Planner-side identity a Portal user is bridged to via `profiles.planner_profile_id` (Feature 001); never created or mapped anew by this feature.
- **Canonical Planner Event Link** (`event_planner_links`, existing, read-only from this feature): the sole source of truth for which Planner event corresponds to a Portal event, reused unchanged from Features 001/004/005.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of manager-permission users can create, edit, reassign, change status of, and delete a task for an event they manage, without leaving the Portal event workspace.
- **SC-002**: 100% of self-assignee-only mutation attempts against a task's title, category, due date, priority, or assignee are rejected, while 100% of their status/remarks changes on their own assigned task succeed.
- **SC-003**: 0% of Bendie-only events expose the Tasks tab or a working direct route to it.
- **SC-004**: 0% of Portal users without a synced Planner profile, or without a qualifying event assignment, can reach Tasks data via the tab or a direct route.
- **SC-005**: 100% of task list rows correctly reflect only tasks belonging to the resolved canonical Planner event — zero cross-event leakage in tested scenarios.
- **SC-006**: 100% of reassignment target lists contain only staff with an active assignment for that specific event.
- **SC-007**: 100% of genuine Planner read/write failures are visually distinguishable from a legitimate empty task list in tested scenarios.
- **SC-008**: 0% of API responses expose a Planner service-role credential, a raw Planner error object, or a column outside the documented safe allowlist.

## Assumptions

- The live Planner schema facts recorded in Context (constraints, triggers, function behavior) reflect the current production Planner database as of 2026-09-17 and are treated as authoritative ground truth for this specification.
- The exact mechanism for how the Portal server performs the mirrored permission check (e.g., a single combined query vs. several) is a planning-level decision, not a specification-level one.
- The existing Planner mobile application and its RPCs (`create_operational_task`, `update_my_task`, `update_operational_task_status`, `get_task_assignable_profiles`, `resolve_profile_for_task`) are unaffected by this feature; Feature 007 introduces its own server-side data-access path against the same tables and does not modify, deprecate, or call these existing functions.
- The controlled Feature 005/006 test fixture (organization "Bendie Planner Sample," events "Stawi Escape," "Stawi Escape — Planner Test," "Stawi Escape — Both Test") remains available for Feature 007's own verification; no fixture changes are made during specification.

## Out of Scope

- Production schedule / run-of-show management (`production_tasks`).
- Bendie agenda editing and Planner agenda editing (`event_agenda_items`).
- Logistics, flights, transfers, accommodation (`transport_logistics`, `all_flights_combined_table`, `hotel_bookings`, vehicle/shuttle tables).
- Participants/passengers (`passengers`, `event_passengers`).
- Checklist (`event_checklist_items`) and vendors (`event_vendor_items`) management.
- Blueprints/documents (`event_blueprints`).
- Notifications (`event_notifications` and related tables) — automatic notification side effects already triggered by existing Planner database triggers on task changes are neither built nor disabled by this feature.
- A multi-event "My Tasks" aggregated view.
- Task dependencies/blocking relationships (no such column exists).
- Any new Planner organization provisioning.
- Any new Planner identity-mapping architecture beyond the existing Feature 001 bridge.
- Any new RBAC system — this feature exclusively mirrors the existing `event_user_assignments` model.
- Any change to Features 001–006 product/mapping semantics, `event_planner_links`, `event_products`, `organization_products`, or URL-authoritative product context.
- Any Portal or Planner schema migration.
