### 2026-09-18 — Manual-acceptance corrective finding (post-save UI lock, MEDIUM)

**Finding**: after saving an edited task (manager) or a self-assignee status/remarks change, the Tasks UI could become stuck — the modal (if reopened) rendered with Save/Cancel permanently disabled, `closeModal` refused to close it (`if (submitting) return`), and the affected row's inline self-assignee controls stayed disabled indefinitely. Normal interaction returned only after a full browser refresh. Task creation was reported unaffected in isolation, but shares the identical code path and was independently confirmed to carry the same defect.

**Root cause**: `planner-tasks/page.tsx`'s `handleSubmit`, `handleDelete`, and `handleSelfAssigneeUpdate` each captured `const requestId = requestIdRef.current` at their start and, in their `finally` block, only called `setSubmitting(false)`/`setBusyTaskId(null)` `if (requestIdRef.current === requestId)`. But `requestIdRef` is the SAME ref `load()` uses for its own, unrelated purpose (discarding a stale/superseded GET response) — and all three handlers call `await load()` on their success path. `load()`'s first line, `const requestId = ++requestIdRef.current`, therefore bumped the shared counter out from under the calling handler's own captured `requestId`, making the `finally` block's equality check false on every successful save/delete and silently skipping the pending-state reset. This was a latent defect in the original `/speckit.implement` code — reusing one ref for two different "is this still valid" questions (load-ordering vs. component-still-mounted) — that only manifested once a real save was actually completed in a browser, which static/live-DB verification during implementation could not exercise (recorded honestly at the time as a genuine live-verification gap).

**Fix**: introduced a dedicated `mountedRef` (`true` on mount, `false` on unmount) used exclusively by the three mutation handlers' own settle/cleanup checks, fully decoupled from `requestIdRef`, which remains untouched and still governs only `load()`'s own GET-response ordering. `setSubmitting`/`setBusyTaskId` now correctly reset after every successful save, delete, and self-assignee update, regardless of `load()`'s internal bookkeeping. File changed: `src/app/portal/events/[eventId]/planner-tasks/page.tsx` only — no other Feature 007 file touched, no server-side or authorization logic affected.

**Part B — refetch-on-return investigation (no fix applied, none needed)**: confirmed via code trace that `EventLayout.tsx`'s capability fetch (T024) depends only on `[currentEvent, organizationId]`, not on the active tab/pathname — it does not re-fire when switching between tabs within the same event. The Tasks *page* itself (`planner-tasks/page.tsx`) does refetch on every navigation into it, because Next.js App Router unmounts/remounts a route's `page.tsx` component on navigation between sibling routes — this is the single, legitimate, expected mount-triggered `GET` this feature was always designed around (FR-043's server-authoritative philosophy), not a loop or duplicate. No caching/SWR/React Query/global state was introduced, per explicit instruction not to optimize without evidence of an actual defect — none was found.
